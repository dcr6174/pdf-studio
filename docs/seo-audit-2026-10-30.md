# PDF Studio SEO audit and fixes

- Audit date: 30 October 2026
- Production site inspected: https://pdf-studio.in
- Repository: https://github.com/dcr6174/pdf-studio

## Scope and baseline evidence

The read-only live crawl fetched all **558 sitemap URLs**, plus six diagnostic URLs. All 558 sitemap pages returned HTTP 200. The XML sitemap is valid and contains no duplicate URLs. `robots.txt` is served as text and references the sitemap. Representative tool pages return headings, metadata and structured data in the HTML; they are not empty JavaScript-only shells.

SVG `<title>` elements were excluded from the search-title findings. A missing slash on the homepage canonical was treated as equivalent, not reported as a defect. The six diagnostic URLs were not included in the indexable-page totals.

No production deployment, paid campaign, Google Search Console submission or document processing was performed by the audit.

## Confirmed issues addressed

| Priority | Evidence before changes | Fix |
| --- | --- | --- |
| High | `/tools/pdf-editor` redirected to `/tools/edit-pdf`; that destination returned 404. Three crawled pages linked to `/tools/edit-pdf`. | Both legacy URLs resolve directly to `/tools/add-text-and-images`. A regression checks every alias destination against the real tool catalogue. |
| High | Invalid tool URLs returned a correct HTTP 404 but contained both `noindex` and `index, follow`, plus the homepage canonical. | Remove the root-level explicit indexing directive; provide error-specific metadata with no canonical; add `X-Robots-Tag: noindex, follow` to HTML errors at the worker boundary. |
| High | 78 sitemap pages had no incoming HTML anchors from the crawled pages. Most were hidden behind catalogue filters. This is a discovery gap, not proof Google never indexed them. | Add server-rendered, user-accessible expandable directories to Studio Lab and Play Studio. All 100 active games now have ordinary anchors before filters are used. |
| Medium | 72 duplicate description groups affected 144 tool/guide pages. | Give instruction pages guide-specific descriptions, titles and consistent search/social metadata instead of reusing the interactive tool's snippet. |
| Medium | Four handwriting guides inherited the homepage `og:url` and sharing text. | Use page-specific guide metadata and the guide's own canonical and social URL. |
| Medium | Two password-protection articles had exactly the same search title. | Distinguish the how-to article from the practical document-sharing example in the actual article catalogue and headings. |
| Medium | `/lab/remove-watermark` repeated `PDF Studio` twice in its title. | Prevent a pre-branded title from receiving the root title template again. |
| Medium | Guides and other aliases used temporary route redirects; internal links pointed through obsolete paths. | Centralize permanent canonical redirects and normalize native internal anchors, preserving query strings and fragments. API and mutation requests are excluded. |
| Medium | Blog pages used website-style Open Graph metadata, and their visible breadcrumb navigation lacked matching breadcrumb structured data. | Set article Open Graph metadata using the existing publication dates, and add per-article `BreadcrumbList` JSON-LD. |
| Low | The homepage had separate mobile and desktop H1s; practice sheets nested another main landmark and H1 inside their parent page. | Provide one shared homepage H1 outside responsive containers; use an embedded section and H2 for the worksheet editor. |
| Maintenance | The committed sitemap could retain legacy guide/export paths even though those routes redirect. | Apply canonical normalization to tool and guide sitemap paths, regenerate the sitemap, and retain content-fingerprint-based dates rather than changing dates on every build. |

## Build safety

The original Next.js dependency was blocked by the package security policy during installation. The compatible patched Next.js/ESLint version is now 16.4.3; the React/React DOM/server renderer versions are aligned at 19.3.1. The existing consumers' DOMPurify dependency is constrained to the patched 3.4.17 release. The project keeps its existing framework and lockfile; no security policy was bypassed.

Three hook dependency warnings exposed by the updated lint toolchain were corrected without changing game engines or save formats.

On branch push, GitHub reported **99 dependency alerts on the default branch**: 4 critical, 43 high, 39 moderate and 13 low. That is GitHub's default-branch summary, not a measured remaining count for this review branch. The security-policy-driven updates above may resolve some alerts, but this SEO change does not establish that all dependency vulnerabilities are fixed. Review the remaining alerts before release.

The separate [dependency security review](dependency-security-audit-2026-10-30.md)
records the actual post-merge GitHub alerts, targeted remediation, branch-only
audit results and exact remaining moderate/low risks. It does not imply this
separate review PR has merged or been deployed.

## Regression protection

Run these from the repository root:

```sh
npm ci
npm run lint
npx tsc --noEmit
npm run build:public
npm run verify:seo
npm run verify:seo:rendered
```

The SEO checks cover:

- One-hop canonical aliases and valid destinations.
- Permanent redirect inputs, queries, fragments and method exclusions.
- Native internal links that avoid broken aliases.
- Unique guide snippets and matching canonical/Open Graph/Twitter metadata.
- Error metadata and the error-response robots header.
- All 100 games' server-rendered catalogue links.
- Standalone versus embedded handwriting landmarks and headings.
- Canonical, unique sitemap entries and exclusion of private/test routes.

The existing repository-quality workflow runs the new SEO regressions after generation/build.

### Verified on the review branch

Lint, TypeScript and the production build completed successfully. The actual built Cloudflare worker was then exercised locally, without deploying or using a remote database:

- All 558 sitemap pages: HTTP 200, one document title, one H1, self-referencing canonical, correct social URL and parseable JSON-LD.
- No duplicate page titles or descriptions across those 558 pages.
- No sitemap pages without an incoming HTML anchor.
- All nine tested legacy URL variants: one permanent redirect to an HTTP 200 destination.
- All four tested missing-page variants: HTTP 404, error-specific title, `noindex` metadata and header, no conflicting `index` directive and no homepage canonical.

These are branch/build results, not a claim that production already has the changes.

## Release verification

Changes are on a separate review branch, not automatically deployed. After review and release:

1. Check `/tools/pdf-editor`, `/tools/edit-pdf`, `/guides/jpg-to-pdf`, `/tools/html-to-pdf`, `/prove-it` and trailing-slash URLs. Each should have at most one permanent redirect to a valid page.
2. Check a nonexistent tool and a nonexistent top-level page: HTTP 404, no homepage canonical, no `index` directive, and a `noindex` response header.
3. Inspect page source on a tool, its guide, a handwriting guide and an article. Verify page-specific titles, snippets, canonical/social URLs and valid JSON-LD.
4. Confirm the two expandable catalogue directories work with JavaScript disabled.
5. Submit or refresh the sitemap in Google Search Console and inspect representative URLs.

## What this does not establish

- A successful HTTP crawl does not prove Google has indexed or ranked a URL. Search Console access is needed for Google's actual coverage, canonical selections, queries and impressions.
- No field Core Web Vitals score, mobile Lighthouse score or backlink profile is claimed. Those need separate measurement.
- Similar tool and guide pages can legitimately serve different intents. Unique snippets are not a substitute for useful content. Existing articles that repeat the same steps should be reviewed for original worked examples, supported limitations and selective consolidation; this change does not invent evidence, delete articles or mass-publish new pages.
- Structured data does not guarantee a rich result. In particular, general sites should not expect FAQ or HowTo rich results solely because they include those schema types.
- No ad account was linked, no campaign was created, and no spending was authorized.
