# Arcade implementation rules
- The shared GamePreferences boundary owns device-local settings and one-tap returning play; allowlisted controls preserve existing game engines and save formats across all 100 games.
- Every arcade game is wrapped by the shared frame in `components/game-frame-core.ts` (via `GamePreferences`); add game-wide UI there instead of per game. Progress/XP/missions/daily/hall-of-fame rules live in `lib/arcade-progress.ts`, covered by `checks/verify-arcade-progress.mjs`. Why: one frame keeps 100 games consistent.
- Games tell the frame their own phase, score, best, win/loss and live readout through `lib/arcade-session.ts` (React side: `components/use-arcade-session.ts`); the frame sends pause/resume/restart/sound back as commands and never infers state from page text or CSS classes. Rules are covered by `checks/verify-arcade-session.mjs`. Why: guessed game-over detection mis-scored rounds and missed end cards.
- Play surfaces size themselves to `--gf-avail` (height left under the shared bar) in `components/game-screen.css`, keeping their aspect ratio; DOM boards without such a rule are fitted by the frame (zoom, then narrowing), and phones held sideways get a tip instead of clipped play. Preserve engine coordinates and local saves. Why: screen use must improve without changing scoring or breaking inputs.
- All game sound goes through the buses in `lib/arcade-mixer.ts` (master, effects, interface, ambience) with saved volumes; new cues are synthesized, not external files. Why: one set of volume sliders for every game and no licensing risk.
- Keep an evidence matrix under `docs/arcade-audit`; distinguish smoke loading from meaningful gameplay and unresolved cases, and say how each result was reached (random input, hints, legal moves). Why: a 100-route count is not proof of 100 complete games.
